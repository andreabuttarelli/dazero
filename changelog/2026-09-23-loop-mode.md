# Loop mode: generate every combination, not one

Producing a shoot means N models × N environments × N garments, not one image at a time. The
canvas already generates one thing per click (`runGenNode`); this adds the combination layer on
top of it, without a second engine.

## The model

- **A wire has a mode**: `fixed` (default, today's behaviour — every iteration sees it) or
  `iterate` (one axis of the combination). Lives on `nodes_connections.mode`, not on the source
  node — the same `list` can feed one wire fixed and another iterated.
- **A `list` node** holds N items (`item_kind`: `image` or `text`, never mixed), each either an
  `asset_id` (dragged in) or a `text` line. Feeds a `fixed` wire with every item (same rule an
  `influencer`'s multiple views already follow); feeds an `iterate` wire one item per iteration.
- **A `select` node** picks exactly one item back out of a `list`, by a 1-based `index` — the
  fast path is clicking a thumbnail inside the node. Its medium follows the list it reads
  (`item_kind`); it is NOT list-valued, so it connects wherever a single node would. Out of
  range, empty list, or no list feeding it: contributes nothing, reported via `rejected`, never a
  silent clamp to the last item.
- **Combination**: cartesian product by default (`loop-plan.ts::planCombinations`, first axis
  varies slowest); `zip` pairs indices 1st-with-1st, shortest axis wins and says so
  (`shortestWins`). No axes at all: plain `repeat N` variants of the same prompt.
- **Caps**: `LOOP_CONFIRM_ABOVE = 50`, `LOOP_MAX = 1000` (`loop-plan.ts::loopSafety`) — run at the
  click up to 50, explicit `confirm: true`/`confirm=1` above that, refused outright above 1000.
  Cost (`loop-cost.ts::estimateLoopCredits`, off the same `IMAGE_CREDITS`/`videoCredits`/new
  `TEXT_NODE_CREDITS` content-cost.ts already uses for a post) is checked for the WHOLE loop
  against the org's remaining balance before the first combination runs, not discovered empty
  halfway.

## Execution — a durable queue, not one big request

**First cut ran every combination sequentially inside one HTTP request, and it was wrong**: an
image takes 40-70s, and at `maxDuration` 300s (the same ceiling `run` uses) only ~5-15
combinations could finish before Vercel kills the request — the 50/1000 safety caps promised a
count the executor could not actually deliver, and everything past whatever fit would silently
never run or resume. Caught in review before it shipped; rebuilt as a queue the existing
per-minute cron drains.

`loop.ts::enqueueLoop` validates, gates the WHOLE loop's cost, creates the output `list` node
with one `queued` placeholder item per combination (so progress is visible from the first
instant), writes one `node_runs` "ticket" row per combination (`status: 'running'`,
`params.loop = {phase: 'queued', combination, outputListNodeId, …}`), and **returns — it runs
nothing**. `drainLoopQueue`, called from `canvas/runs/tick` (already cron'd every minute,
alongside `expireStuckRuns`/`reconcileVideoNodeRuns`), claims a bounded batch (3 per tick,
`maxDuration: 300` now set explicitly on that route — it never had one) atomically via the
existing `claimRun` (the same `running → finishing` guard `reconcileVideoNodeRuns` already uses
against double-billing), runs each ticket through `runGenNode` — the exact function the Generate
button and `run_node_generation` call, no copy — and closes it with `completeRun`/`failRun`,
patching only that combination's item in the output list. A failed combination never stops the
batch. A 1000-combination loop now finishes over many minutes instead of never finishing at all.

`cancelLoop` claims and fails only still-`queued` tickets (`error: 'cancelled'`); one a tick has
already claimed finishes regardless — same "completed results survive" rule. `retryLoopCombination`
stays synchronous: retrying one combination is a single generation, not a durability problem.

No new column or table: a ticket is a `node_runs` row distinguished by `params.loop.phase`, the
same trick `queuedVideoRuns` already used (`status` + a marker field) rather than a jsonb path
filter — nothing in this repo queries by jsonb path, and this doesn't start. `expireStuckRuns`
(the 6-minute stale sweep) was taught to skip `queued` tickets: a long backlog waits its turn
longer than that without being "lost."

## What's wired, what isn't yet

- `GenNode.svelte`: a `repeat` field (`data.params.repeat`, alongside `aspectRatio`/`duration`/
  `audio` — one params object, not two places) and a "Loop"/"Annulla loop (N)" button that calls
  `loop_plan` (free preview) then, if `needs_confirmation`, a native `confirm()` with the count
  and cost, then `run_loop` (enqueues) or `cancel_loop`. Traced: click → `runLoop()`
  (`+page.svelte`) → `POST ?/loop_plan` and `POST ?/run_loop` (`+page.server.ts` actions) →
  `planLoop`/`enqueueLoop` (`loop.ts`) → `node_runs` tickets → cron `canvas/runs/tick` →
  `drainLoopQueue` → `runGenNode` (`generate.ts`, unchanged). Progress shown via
  `loopQueuedByNode`, counted from the same `node_runs` rows the page already loads.
- Route + MCP: `GET/POST/DELETE /api/v1/org/nodes/:id/loop`, MCP tools `run_node_loop`/
  `preview_node_loop`/`cancel_node_loop` — same engine, same caps, `confirm: true` required the
  same way above 50.
- **`nodes_type_check` and `nodes_connections_mode_check` are NOT applied**
  (`supabase/canvas-migrations/20260923_loop_nodes.sql`, pending). Until they are: creating a
  `list`/`select` node or writing `nodes_connections.mode` would fail live (42703/23514) —
  learned the hard way mid-session, when `repos/canvas.ts` briefly selected/inserted `mode`
  before the migration existed and broke every canvas load with a 42809 (Postgres read the
  unknown column as the `mode()` aggregate function). Fixed in `fe41ffa1`; the discipline from
  then on: every write to `mode` (`createConnection`, `setConnectionMode`) and to the two new
  node types stays unreached from any route until Andrea applies the migration. Axis resolution
  therefore always sees zero `iterate` wires today — every loop runs as `repeat N` variants,
  which is real and tested, not a stub. `setConnectionMode` exists and is tested but is not
  called from anywhere yet — wiring a wire-mode toggle into the UI before the column exists would
  reproduce the exact bug the hotfix just closed. The `list`/`select` node components
  (drag-in, thumbnail-click-to-select) are not yet built for the same reason: nothing can create
  one until the CHECK constraint allows the type.
